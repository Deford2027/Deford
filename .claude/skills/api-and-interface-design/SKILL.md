# API and interface design

Роль: архитектор контракта, который делает границу предсказуемой для потребителя, проверяемой и безопасной при повторах и изменениях.

## Входы

- потребители и их реальные сценарии;
- существующий контракт и наблюдаемое поведение;
- данные, эффекты, требования авторизации и приватности;
- ограничения совместимости, нагрузки и доставки.

Сначала найди существующих потребителей, схемы, тесты и remote IDs. Не делай вывод о безопасности breaking change только по отсутствию документированного использования: наблюдаемое поведение могло стать зависимостью.

## Порядок

1. Опиши границу: кто вызывает, что считается одним намерением, какие состояния и побочные эффекты пересекаются.
2. До реализации зафиксируй типизированные вход, успешный выход и единую ошибку: стабильный машинный код, безопасное сообщение, допустимые детали.
3. Валидируй недоверенные данные на внешней границе: пользовательский ввод, конфигурацию, webhook, ответ стороннего API, очередь. Сохранённый пользовательский или импортированный контент остаётся недоверенным на SQL/HTML/shell/URL и других опасных sinks — собственная БД не делает его безопасным. Не размазывай повторную валидацию по уже типизированным внутренним функциям без конкретного риска.
4. Проверь совместимость всех наблюдаемых полей, порядка, nullability, статусов и ошибок. Предпочитай добавочное необязательное расширение; breaking change требует миграции или явно принятой границы.
5. Для списков выбери пагинацию, порядок и стабильный cursor/page-контракт по реальному объёму, а не автоматически.
6. Для изменяющего состояние или дорогого действия определи семантику повторов. Если обещана идемпотентность: ключ отражает одно намерение, атомарно захватывается уникальным ограничением, связан с hash запроса, имеет достаточный TTL и предсказуемо обрабатывает in-flight дубль.
7. Моделируй три результата внешнего эффекта: успех, подтверждённый отказ, неизвестный исход. Timeout не доказывает, что эффект не применился; не повторяй его вслепую.
8. Подготовь контрактные тесты для happy/error/auth/retry/unknown и документацию потребителя. Live, платные, destructive или внешние вызовы выполняй только в разрешённой среде.

## Минимальный артефакт

```text
Operation: <name and intent>
Input / validation: <schema and limits>
Success: <status/event + typed body>
Errors: <stable codes and safe details>
Auth: <actor and scope>
Retries: <safe/unsafe; key, atomic claim, TTL, in-flight, unknown>
Compatibility: <consumers and migration>
Evidence: <contract tests / runtime check>
```

## Запрещено / разрешено

| Запрещено | Разрешено |
|---|---|
| Начать с handler и придумать контракт по ходу | Сначала зафиксировать потребителя и контракт |
| Протекать stack trace, secret или внутренней моделью | Стабильный error code и безопасное сообщение |
| Считать заголовок `Idempotency-Key` реализацией идемпотентности | Атомарный claim, request hash, replay policy и достаточный TTL |
| После timeout повторить денежный/live-эффект как «ошибку» | Состояние unknown, reconciliation и повтор только по доказанной политике |
| Всегда добавлять version/pagination «по шаблону» | Выбрать их по совместимости, объёму и реальным потребителям |
| Менять provider/model/permissions ради удобства | Сохранить заданную среду; запросить только недостающую власть |

Правильно: повтор одного события публикации использует стабильный ID намерения и возвращает уже сохранённый результат; другой payload с тем же ID отклоняется.

Неправильно: retry-слой генерирует новый UUID на каждую попытку и после timeout повторно создаёт запись.

## Реальный пример владельца

В Tilda Feed успешный API-save или рост счётчика не равны готовой публикации. Контракт доставки должен отдельно хранить `CMS-saved` и `publicly-published`, сохранять исходный record ID и структуру HTML, а проверка — подтвердить сохранённый тип блока, decoded HTML, metadata и точный публичный URL. Повтор не создаёт дубликат.

## Проверяемый выход

- `PASS`: контракт однозначен для потребителя; boundary validation, ошибки, auth, совместимость и retry/unknown покрыты применимыми проверками.
- `FAIL`: есть несовместимое или двусмысленное поведение, небезопасный повтор, потеря структуры/данных либо обязательный контрактный тест не проходит.
- `INCONCLUSIVE`: не найдены потребители, нет доступа к схеме/runtime или неизвестен исход эффекта; явно указано, что нельзя подтвердить.

Главное: публичная граница — обязательство; проектируй её от намерения потребителя и не превращай неизвестный исход в безопасный retry.

# Наблюдаемость

Ты делаешь критический runtime-путь диагностируемым по фактам, не раскрывая секреты и персональные данные.

## Вход и порядок

Нужны изменяемый поток, его пользователи/операторы, зависимости, failure modes, действующий telemetry stack и ограничения данных.

1. Сформулируй 2–4 вопроса, на которые оператор должен ответить при сбое: что сломалось, где, для кого и с какого момента.
2. Для каждого вопроса выбери минимальный сигнал: метрика показывает факт деградации, trace — место, структурированный log — причину. Не собирай сигнал без потребителя.
3. Определи стабильные event names, correlation ID и его перенос через HTTP/queue/async boundaries. Поля — allowlist; тела запросов, auth headers, secrets и неочищенные PII запрещены.
4. Для endpoints/dependencies используй RED (rate, errors, duration), для ресурсов/очередей — USE (utilization, saturation, errors), если они действительно применимы. Избегай меток высокой кардинальности.
5. Алерт создавай только для наблюдаемого пользовательского симптома с владельцем, порогом, окном и коротким runbook. Инфраструктурные причины без срочного действия оставляй на dashboard/ticket.
6. Проверь телеметрию: вызови безопасный тестовый запрос или контролируемую ошибку в разрешённой среде; найди событие по correlation ID, метрику с ожидаемыми labels и целую trace-цепочку.

Не подключай внешний telemetry provider, не отправляй данные и не меняй production без явного разрешения. Если stack неизвестен, опиши vendor-neutral контракт и пометь интеграцию `INCONCLUSIVE`.

## Выход

Верни таблицу `операторский вопрос → сигнал → поля/labels → порог → проверка`, правила редактирования данных, dashboard/runbook и результат проверки.

- **PASS** — каждый заявленный сигнал реально наблюдался и отвечает на конкретный вопрос без утечки данных.
- **FAIL** — сигнал отсутствует/неверен, корреляция рвётся, алерт неоперационален или данные небезопасны.
- **INCONCLUSIVE** — доступ к среде/aggregator отсутствует; дизайн дан, runtime не подтверждён.

## Запрещено / разрешено

| Запрещено | Разрешено |
|---|---|
| Логировать весь request/response «для отладки» | Allowlist полей и маскирование чувствительных значений |
| Считать наличие кода instrumentation доказательством | Найти реальный сигнал в разрешённой среде |
| Алертить на всё или на среднее | Выбрать симптом и p95/p99, если распределение важно |
| Добавлять user ID, URL или error text в labels | Стабильные route/status/provider classes |

Правильно: worker пишет `job_completed` с correlation ID, duration, provider и sanitized status; очередь имеет depth/age, а тестовая ошибка находится в логах. Неправильно: `console.log(request)` и алерт «CPU > 80%» без пользовательского эффекта и runbook.

Пример владельца: флаг очереди не доказывает выпуск результата — нужно проверить consumer, enabling flags и физический output; наблюдаемость должна дать эти три доказательства.

Главное: телеметрия отвечает на эксплуатационный вопрос и сама проходит runtime-проверку.

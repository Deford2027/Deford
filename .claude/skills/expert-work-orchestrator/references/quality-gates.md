# Условные quality gates

Выбирай gates до исполнения по изменяемому риску. Не запускай четырёх постоянных агентов для каждого шага: один проверяющий может оценить несколько осей, если его контракт остаётся узким и понятным.

## Матрица

| Gate | Когда нужен | Минимальное доказательство |
|---|---|---|
| Build/static | Код, runtime-config, dependencies | Реальная команда репозитория и exit status |
| Behavior/tests | Новое или изменённое поведение, bugfix | Focused test; для bugfix — безопасно доступный baseline/reproducer даёт RED, исправление — GREEN; иначе зафиксировать альтернативное доказательство и ограничение |
| Architecture | Границы модулей, API, data flow, миграция | Импорты/вызовы, контракты, consumer map и дифф |
| Security/privacy | Входы, auth, secrets, PII, сеть, dependencies | Threat-relevant путь данных и профильный security verdict |
| Plan/coverage | Серия шагов или формальные acceptance criteria | Каждый критерий связан с артефактом или честным unresolved |
| Runtime | UI, endpoint, service, worker, queue | Happy path, validation/error path, access control при наличии и проверка логов |
| Data/migration | Изменение схемы, данных или формата | Backup/restore или rollback, паритет до/после, измеренные счётчики |
| Release | Боевая публикация/деплой | Точный target, saved/live state, health, rollback readiness и post-check |

## Вердикт

- `PASS` — выбранный gate выполнен первичными доказательствами.
- `FAIL` — найден подтверждённый дефект или нарушен обязательный критерий.
- `INCONCLUSIVE` — проверка недоступна, неполна или доказательства противоречат друг другу. Это не PASS.

## Выбор по риску

| Изменение | Gates |
|---|---|
| Только документация без изменения поведения | Plan/coverage; build только если документация собирается |
| Код, меняющий поведение | Build/static + Behavior/tests; Architecture при изменении границ |
| Auth, PII, secrets или внешний ввод | Security/privacy + Behavior/tests + Runtime |
| Миграция данных | Data/migration + Behavior/tests + Runtime; Security/privacy при чувствительных данных |
| Публичный релиз | Release + релевантные Runtime/Behavior проверки |

## Запрещено / разрешено

| Запрещено | Разрешено |
|---|---|
| Запускать все gates ритуально | Выбрать минимальный набор, покрывающий реальный риск |
| Считать самоотчёт исполнителя независимой проверкой | Дать ревизору исходную задачу, артефакт и критерии |
| Подменять недоступную проверку уверенным PASS | Вернуть INCONCLUSIVE и назвать недостающее доказательство |
| Повторять успешный gate без нового изменения | Повторить только затронутые gates после исправления |

Правильно: изменение API получает contract/consumer проверку и focused tests. Неправильно: запускать security review для правки орфографии или считать зелёный lint доказательством runtime-поведения.

Пример владельца: при публикации статьи успешный save или флаг очереди не доказывает релиз — нужны точный публичный URL, контент, canonical/robots/sitemap и desktop/mobile результат.

Главное: проверка пропорциональна риску, но каждый заявленный результат имеет наблюдаемое доказательство.

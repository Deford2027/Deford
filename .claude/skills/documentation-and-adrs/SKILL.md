# Документация и ADR

Ты сохраняешь только то знание, которое помогает следующему человеку принять решение или выполнить действие по фактической системе.

## Порядок

1. Определи читателя и его действие: начать работу, вызвать API, восстановить сервис, понять решение или продолжить проект.
2. Найди один действующий source of truth и ближайший аналог. Обновляй его вместо создания конкурирующего README/status/handoff.
3. Проверь каждое техническое утверждение по коду, конфигурации, команде, схеме или первичному источнику. Не описывай намерение как существующее поведение.
4. Пиши минимальную форму:
   - how-to: prerequisites, точные шаги, ожидаемый результат, ошибки/восстановление;
   - reference: входы, выходы, ограничения, примеры и версия;
   - runbook: symptom, первая безопасная диагностика, решение, rollback/escalation;
   - ADR: context, decision, significant alternatives, consequences и status.
5. ADR нужен, когда решение меняет архитектурную границу, трудно отменяется или его причина иначе потеряется. Обычную правку и историю изменений в ADR не превращай.
6. Проверь ссылки, команды и пример в разрешённой среде. Если команда не запускалась, явно пометь это; documentation lint не доказывает поведение продукта.
7. Удали устаревшее/противоречивое описание в том же scope либо укажи точный долг и владельца.

## README проекта для GitHub

Когда владелец просит «описать проект как продукт» или привести Git-репозитории к понятному виду, используй существующий README как входную страницу. Возьми из удачного примера способ объяснения, а факты проверь заново в данном репозитории. Не копируй заявления о функциях, деплое и готовности из чужого README.

1. Начни с назначения для пользователя и текущего режима. Отдельно назови реально проверенные возможности и то, что ещё планируется или не проверено; устаревающий оперативный статус оставь в одном действующем проектном источнике с ссылкой из README.
2. Покажи путь пользователя, действительную схему компонентов, стек и карту основных папок. Схему будущего маршрута явно подпиши как целевую. Не превращай список файлов в каталог без объяснения их роли.
3. Дай самый короткий проверяемый вход: запуск или локальную проверку, нужные условия и ожидаемый результат. Сохрани существенные рабочие инструкции старого README либо перенеси их в уже существующий документ с рабочей ссылкой.
4. Проверь каждую относительную ссылку, команду и заявленную функцию. Отдели локальные тесты от живой доставки и публикации. В пакетном обновлении исключи сторонние клоны и пустые репозитории до выяснения их владельца и назначения; не создавай одинаковые README по шаблону для разных продуктов.

Пример из проекта владельца «Омниканальный ИИ-помощник»: README показывает проверенный Chatwoot webhook и owner-only «Сириус», целевой маршрут помечает отдельно и ссылается на `PROJECT_STATUS.md` за актуальными блокерами. Фраза «все каналы подключены» была бы неверной, даже если схема будущих каналов уже нарисована.

## Выход

Дай путь, аудиторию, проверенные источники, изменённое знание, выполненную проверку и известные ограничения.

- **PASS** — документ ведёт к воспроизводимому результату и согласован с текущей системой.
- **FAIL** — команда/ссылка/контракт неверны, есть противоречие или создан второй source of truth.
- **INCONCLUSIVE** — runtime или внешний источник недоступен; непроверенное утверждение отмечено.

| Запрещено | Разрешено |
|---|---|
| Документировать выдуманный будущий state как текущий | Разделить current, decision и planned work |
| Создавать новый status-файл на каждый шаг | Обновлять один существующий журнал |
| Пересказывать код без задачи читателя | Дать контракт, пример и способ проверки |
| Называть документ dashboard/UI | Честно назвать артефакт документацией |

Правильно: runbook содержит первую read-only команду, ожидаемый сигнал и безопасный rollback. Неправильно: «перезапустите сервис» без target, причины и post-check.

Пример владельца: разрозненное состояние проекта надо свести в один owner-readable источник с логикой, блокерами, долгом и следующим шагом — но не выдавать Markdown за развёрнутый dashboard.

Главное: документ ценен только если он соответствует системе и помогает выполнить конкретное действие.

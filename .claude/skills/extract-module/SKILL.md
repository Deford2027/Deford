# Вынос одного модуля

Это переезд кода с сохранением поведения. Один подход — один модуль — один проверенный коммит.

## Порядок

1. Прочитай правила проекта; проверь Git и незакоммиченные изменения. Зафиксируй исходные результаты доступных проверок, точные свои пути и способ отмены только своего переноса.
2. Выбери самостоятельный фрагмент: ориентир 200–800 строк, **≤5 внешних связей**. Для большого файла обязательно используй `code-researcher`. При >5 связях выбери другой; если карта неизвестна — сначала исследуй.
3. Составь карту: внешние символы, ресурсы, глобальные настройки, кто вызывает, порядок импорта/регистрации, дубли имён, относительные пути. Повторное объявление функции/константы — **стоп и отдельный разбор**. Не полагайся на «последнее определение побеждает»: сохранённые ссылки могут жить иначе.
4. Включи в scope новый модуль, исходник, потребителей, необходимые тесты и списки файлов в сборке/проверках/аудитах. Если шаг трогает >3 файлов кода — останови его и предложи разбиение; не пропускай интеграцию ради лимита. Новый код не расширяет файл за 800 строк.
5. Перенеси тела без попутной переработки. Исправь только необходимые импорты/подключение; удали перенесённую копию, не оставляй закомментированной. Сохрани публичные имена и контракт.
6. Повтори baseline и существенные сценарии: результаты/ошибки, потребители, ресурсы через `__file__`, изменяемые настройки, циклические импорты, однократность регистрации и сборка. Равные тела функций — дополнительное свидетельство, не доказательство поведения.
7. При **новой** регрессии отмени только свой перенос, установи причину, повтори меньшим фрагментом. Не исправляй несвязанный баг; запиши его в существующий реестр. Чужие изменения и данные сохраняй.
8. Назначь независимого `change-reviewer`, передав задачу, критерии, базовую ревизию и точный diff. До его результата не объявляй перенос проверенным. При настоящем блокере покажи причину; не повторяй неизменённый неуспешный подход без новых данных.
9. Покажи проверку владельцу и создай отдельный коммит только своих изменений. Заверши задание; следующий кусок — новое конкретное задание и свежий контекст. Для заранее заказанной серии см. пункт 3 [общих ограничений](../expert-work-orchestrator/references/owner-constraints.md).

## Запрещено / разрешено

| Запрещено | Разрешено |
|---|---|
| Менять имена, аргументы, сообщения и формат ответов | Сохранить контракт и скорректировать только подключение |
| Чинить баг или «причёсывать» соседнее по дороге | Записать долг и закончить чистый перенос |
| Два модуля за один подход | Один модуль, проверка, ревизор, коммит, стоп |
| Откатить всё рабочее дерево | Отменить собственный patch, не затронув владельца |

## Правильно / неправильно

| Правильно | Неправильно |
|---|---|
| До/после проверена изменяемая настройка в реально вызываемой функции | Текст функции совпал, значит поведение совпало |
| Обновлён нужный список модулей сборки | Новый файл существует, но сборка его не видит |

Источник: эксперт отдельно отметил дубли объявлений и включение нового файла в проверки; это сохранённые обязательные условия.

Главное: один чистый перенос, ≤5 внешних связей, ≤3 файлов кода за шаг, доказанное поведение и независимый ревизор.

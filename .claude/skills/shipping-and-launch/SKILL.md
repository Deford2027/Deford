# Выпуск и запуск

Ты доводишь уже разрешённый релиз до подтверждённого live-состояния с ограниченным blast radius и рабочим откатом.

## До изменения

Зафиксируй точный target/версию/ID, baseline health, критерии успеха и остановки, зависимые системы, владельца решения об откате, backup/rollback и различие `saved`, `deployed`, `publicly available`. Боевой deploy, публикация, переключение трафика или уведомление внешних людей требуют явного поручения.

## Порядок

1. Проверь релизный артефакт: точная ревизия, применимые tests/security/data gates, конфигурация и отсутствие незаявленных изменений.
2. Выбери стратегию по реальному риску: обычный deploy для малого обратимого изменения; canary/rolling/blue-green/feature flag — только когда инфраструктура поддерживает это и выигрыш оправдан.
3. Перед data/schema change докажи совместимость старой и новой версии и порядок expand/migrate/contract; необратимая миграция без проверенного восстановления блокирует выпуск.
4. Выполни первый минимальный slice/record и полностью проверь его в целевой системе до batch/полного трафика.
5. После выпуска проверь exact identity/URL/version, основной сценарий, validation/error path, access control при наличии, health/latency/errors/queue age и логи. Для UI/publication проверь desktop/mobile и фактический публичный контент.
6. При пересечении stop threshold остановись и откати; после rollback повторно проверь health и целостность данных. Не продолжай batch после нарушения инварианта.
7. Зафиксируй outcome, доказательства, остаточный риск и следующий наблюдаемый checkpoint. Не объявляй готовность по команде с exit 0, флагу очереди или локальному артефакту.

## Вердикт

- **PASS** — exact target доступен, критерии live-проверки выполнены и rollback готов/проверен пропорционально риску.
- **FAIL** — инвариант нарушен, health ухудшился, target неверен или live-результат не соответствует артефакту.
- **INCONCLUSIVE** — выпуск не разрешён/недоступен либо post-check нельзя выполнить; локальная готовность указывается отдельно.

| Запрещено | Разрешено |
|---|---|
| Считать deploy command доказательством результата | Проверить целевую систему и пользовательский сценарий |
| Всегда требовать feature flag/canary | Выбирать стратегию по blast radius и возможностям системы |
| Продолжать batch после первого дефекта | Остановить, восстановить инвариант, затем решать о продолжении |
| Смешивать draft, saved и public | Отдельно записать каждое состояние |

Правильно: сохранить rollback snapshot, проверить первый CMS record целиком, затем каждый ID и публичный URL. Неправильно: увидеть 200 у API save и сообщить «опубликовано».

Пример владельца: Tilda-релиз подтверждают точный URL, видимый контент, canonical, sitemap, robots и desktop/mobile; queue/save сами по себе недостаточны.

Главное: релиз завершён только после проверки фактического live-состояния и способности безопасно вернуться назад.

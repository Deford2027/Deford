# Схема проекта

Сервис — визуальный планировщик. Доска в нём **не исполняется**: это
техническое задание, по которому человек или другая нейросеть потом пишет код.
Схема должна быть понятна без пояснений вслух.

## Этот файл обновляется сам

Методичка живёт на сервере и меняется вместе с сервисом. Твоя копия может
обновиться без твоего ведома — если ты или кто-то рядом выполнил команду
обновления. Поэтому не удивляйся, если версия в начале файла отличается
от той, что ты видел час назад: это нормально, значит копия свежая.

## Сначала проверь, не устарел ли этот файл

`GET /api/format` отдаёт `версияМетодички`. Если она **не совпадает**
с `версия-методички` в начале этого файла — значит сервис ушёл вперёд,
а у тебя старая копия. Обнови и перечитай:

```bash
curl -o .claude/skills/схема-проекта/SKILL.md https://arch.viberendered.ru/схема-проекта.md
```

Проверять стоит при первом обращении к схемам в сессии — не чаще.

## Как работать

Всё через обычный HTTP. Токен лежит в `~/.arch-token`, адрес сервиса —
`https://arch.viberendered.ru`.

```bash
# справка о формате: типы блоков, статусы, виды связей, правила
curl -s -H "X-Arch-Token: $(cat ~/.arch-token)" \
     https://arch.viberendered.ru/api/format

# какие доски есть
curl -s -H "X-Arch-Token: $(cat ~/.arch-token)" \
     https://arch.viberendered.ru/api/boards

# прочитать доску целиком
curl -s -H "X-Arch-Token: $(cat ~/.arch-token)" \
     https://arch.viberendered.ru/api/boards/ИД

# завести доску
curl -s -X POST -H "X-Arch-Token: $(cat ~/.arch-token)" \
     -H 'content-type: application/json' \
     -d '{"name":"Название проекта","summary":"О чём он"}' \
     https://arch.viberendered.ru/api/boards

# добавить блоки и связи
curl -s -X PATCH -H "X-Arch-Token: $(cat ~/.arch-token)" \
     -H 'content-type: application/json' \
     -d @операции.json \
     https://arch.viberendered.ru/api/boards/ИД

# посмотреть схему словами — и проверить себя
curl -s -H "X-Arch-Token: $(cat ~/.arch-token)" \
     https://arch.viberendered.ru/api/boards/ИД/text

# ссылка на просмотр без входа — показать человеку
curl -s -X POST -H "X-Arch-Token: $(cat ~/.arch-token)" \
     https://arch.viberendered.ru/api/boards/ИД/share

# удалить доску
curl -s -X DELETE -H "X-Arch-Token: $(cat ~/.arch-token)" \
     https://arch.viberendered.ru/api/boards/ИД
```

**Пачку операций клади в файл** и передавай `-d @файл.json`: в командной
строке кавычки и кириллица ломаются, а из файла уходят как есть.

Если `~/.arch-token` нет — попроси токен у человека (он берёт его в своём
кабинете, вкладка «Нейросеть») и сохрани:
`echo "токен" > ~/.arch-token && chmod 600 ~/.arch-token`

## С чего начинать

1. `GET /api/format` — правила и полное описание формата. **Актуальные правила
   всегда там, а не в этом файле.** Если справка расходится с написанным
   здесь — права справка.
2. `GET /api/boards` — что уже есть.
3. Новый проект — **всегда новая доска**. Не дописывай новый проект в чужую
   схему: два проекта в одной доске нечитаемы.
4. Реши, какая доска нужна. **Схема** — как устроена система: шаги, данные,
   сервисы, развилки; по ней пишут код. **Майндкарта** — дерево: план работ,
   разбор темы, список дел. Просят «майндкарту», «план веткой», «разложи
   по пунктам» — это майндкарта, см. раздел о ней ниже.

## Главное: схему читает человек

Её открывают, чтобы **понять проект за минуту**, а не чтобы изучать неделю.
Сотня блоков с сотней стрелок в одном полотне — это нечитаемо, сколько бы
правильных полей в них ни было.

**Предел — не в числе блоков, а в том, сколько их видно при открытии.**
Держись примерно трёх десятков видимых. Доска на сотню блоков — это нормально,
если разделы свёрнуты; тридцать развёрнутых блоков без разделов — уже полотно.

**Разделов делай пять-семь, не больше.** Внутри каждого — до десятка блоков.
Это не пожелание: проверка считает, сколько блоков станет видно, когда человек
развернёт самый большой раздел. Свалить всё в один свёрнутый раздел не выйдет —
раздел на тридцать блоков разворачивается в такое же полотно.

**Сворачивай разделы:** `data.collapsed: true`. Свёрнутый раздел выглядит
одной карточкой со счётчиком, а связи его блоков с внешним миром схлопываются
в одну стрелку. Человек открывает доску, видит несколько коробок и понимает
устройство целиком — а потом разворачивает то, что ему нужно.

Хорошая большая доска открывается так: **все разделы свёрнуты, кроме
одного-двух главных**. Собрал схему — сверни разделы, прежде чем отдавать.

**Один блок — один заметный шаг**, а не одна строчка кода. Если блоков
выходит много, посмотри, не попали ли в них подробности, которым место
в `note` или в `spec`.

**Связи рисуй только существенные.** Стрелка нужна там, где без неё непонятен
порядок или откуда берутся данные. «Этот блок теоретически связан с тем» —
не повод.

**К общим таблицам и сервисам стрелки не тяни — ставь `uses`.** Это список
id того, чем блок пользуется: таблицы, сервисы, промты, файлы. Ссылка видна
меткой прямо на карточке, а на таблице — счётчиком, сколько блоков её
используют. Именно связи к общим вещам и превращают схему в клубок: их
в проекте десятки, и каждая тянется через весь холст.

Стрелку `read`/`write` оставляй там, где важен порядок: данные появились
здесь, потом попали туда. Важен только факт «этот шаг работает с этой
таблицей» — хватит `uses`.

**Названия короткие**, до двадцати пяти знаков: дальше карточка обрезает.
Подробности — в `note`, точные условия — в `spec`.

## Как выглядит хорошая схема

**Слева направо по ходу работы.** Вход слева, результат справа. Шаг по
горизонтали около 330, по вертикали около 150.

**Начинается с триггера.** Что запускает: расписание, вебхук, действие
человека. В триггер стрелки не входят — с него схема начинается.

**Разделы (`group`) — крупные куски системы.** «Сбор данных», «Обработка»,
«Выдача». Блоки внутри указывают id раздела в поле `parent`, и тогда раздел
таскает их за собой. Раздел создают раньше блоков, которые в нём лежат.
Разделы можно соединять между собой — так видно, какой кусок идёт за каким.

**Общий блок не дублируют.** Если к таблице или сервису обращаются из разных
мест — это один блок, на который ссылаются через `uses`. Две одинаковых
таблицы на схеме означают две разные таблицы в жизни.

**Связи к таблице осмысленные.** `write` — блок пишет, `read` — читает.

**У каждого блока заполнен `spec`:** что приходит на вход, что отдаёт, как
понять, что готово. У триггера входа нет — там хватит «что отдаёт» и признака
готовности, выдумывать вход не нужно. Признак готовности проверяемый, а не «работает хорошо».
Именно `spec` превращает картинку в задание.

**Текст в полях короткий.** Название — несколько слов, `spec` — строка,
подробности — в `note`. Длинные строки на карточке обрезаются.

**Статусы расставлены**, если что-то уже сделано: `idea`, `todo`, `doing`,
`untested`, `done`, `broken`. `untested` — код написан и работает, но живьём
не проверен; в живом проекте это самое частое состояние.

**Где это в коде** — `data.path` у любого блока. Не заводите ради этого
отдельный блок `file` и связь к нему.

## Проверь себя, когда закончил

`GET /api/boards/<id>/text` отдаёт схему словами и внизу перечисляет то, что
бросилось бы в глаза человеку: блоки без названия, ни с чем не соединённые,
пустые разделы, отсутствие триггера, слишком длинные названия. Прочитай
и почини, прежде чем говорить «готово».

И задай себе вопрос честно: **человек, который откроет эту доску первый раз,
поймёт проект за минуту?** Если для этого ему придётся разбирать клубок
стрелок — сверни разделы и убери лишние связи.

Если нужно показать схему человеку — `POST /api/boards/<id>/share` даёт
ссылку, по которой доску видно без входа.

## Чего не делать

- Не оставлять блоки без названия.
- Не тянуть стрелки к разделу: у рамки нет портов.
- Не тянуть стрелку в триггер: входа у него нет.
- У условия на связи `flow` всегда указывать `sourceHandle`: `yes` или `no`,
  а если у него свои ветки в `data.branches` — `id` нужной ветки.
  На `read`, `write` и `ref` ветка не нужна — они идут мимо развилки.
- Не ставить два условия подряд ради трёх исходов: одна развилка
  с `data.branches` на три ветки читается сразу.
- Чтение рисовать **от таблицы к блоку**, запись — от блока к таблице.
- Заметку к триггеру привязывать в обратную сторону: `trigger → note`.
- Не выдумывать типы блоков и виды связей: что бывает, говорит `/api/format`.
- Не делать схему из одних «Действий»: для данных есть таблица, для внешнего
  API — сервис, для задания нейросети — промт, для страницы — экран.
- Не заливать вслепую в непустую доску: сначала прочитай её.

## Как правится

`PATCH /api/boards/<id>` с телом `{"ops": [...]}`. Операции: `addNode`,
`updateNode`, `moveNode`, `deleteNode`, `addEdge`, `updateEdge`, `deleteEdge`,
`setBoard`. Применяются по порядку, и если хоть одна не проходит проверку —
не применяется ничего. Схема не останется собранной наполовину.

Чтобы связать блоки внутри одного запроса, **задавай им id сам**. Ответ
с автоматически выданными id приходит уже после того, как вся пачка применена.

Снять поле: передать в `patch` значение `null`.

## Майндкарта

Доска с `"kind": "mindmap"` — дерево веток от одного корня. Стрелок,
координат, разделов и `spec` в ней нет: ветка растёт из родителя (`parent`),
место среди соседей — `order`, раскладывает редактор сам.

```bash
# завести — корень с id root появится сразу
curl -s -X POST -H "X-Arch-Token: $(cat ~/.arch-token)" \
     -H 'content-type: application/json' \
     -d '{"name":"План запуска","kind":"mindmap"}' \
     https://arch.viberendered.ru/api/boards
```

Ветки добавляются пачкой; `type` писать не нужно. Чтобы вешать ветки на
только что созданную, задай ей `id` сам:

```json
{ "ops": [
  { "op": "addNode", "node": { "id": "seo", "parent": "root", "title": "SEO-контент-завод",
    "status": "doing", "data": { "who": "Claude", "hours": 6 } } },
  { "op": "addNode", "node": { "parent": "seo", "title": "Собрать запросы",
    "note": "через вордстат и подсказки поиска" } },
  { "op": "addNode", "node": { "parent": "root", "title": "Видео для YouTube" } }
] }
```

- Перенести ветку — `updateNode` с другим `parent`; поменять порядок — `order`.
- `deleteNode` уносит ветку **со всем, что в ней**. Корень не удаляется.
- Прочитать целиком — `GET /api/boards/<id>/text`: дерево с отступами, у каждой
  ветки её `#id`.
- Название ветки — короткое, суть в одну строку. Подробности — в `note`.
- Если майндкарту ведёт человек, **его структуру не переписывай**: добавляй
  ветки внутрь его веток и спрашивай, прежде чем переносить или удалять.

## Если не пускает

- **`cat: ~/.arch-token: No such file or directory`** — файла с токеном нет,
  это самый частый случай у новичка. Попроси токен у человека: он берёт его
  в кабинете, кнопка с именем в шапке → вкладка «Нейросеть». Потом положи:
  `echo "токен" > ~/.arch-token && chmod 600 ~/.arch-token`
- `401` — токен не подошёл. Чаще всего его заменили в кабинете, а в файле
  остался старый. Возьми новый там же и перезапиши файл той же командой.
- `404` на доску — либо опечатка в id, либо доска чужая и не открыта этому
  аккаунту. Ответ одинаковый намеренно.
- `403` — доска открыта только на чтение, попроси у владельца право на правку.
- `400` — нарушено правило формата, в тексте сказано какое и с каким блоком.

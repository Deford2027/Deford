# Совместимая миграция

Ты заменяешь контракт или данные без скрытого обрыва потребителей и без преждевременного удаления старого пути.

## Порядок

1. Зафиксируй old/new contract, владельца, точную область и причину. Найди всех реальных consumers: imports/calls, jobs, внешние клиенты, сохранённые данные, docs/examples и operational tooling.
2. Установи baseline использования старого пути. Если telemetry нет, добавь безопасное измерение либо честно пометь неизвестную внешнюю зависимость.
3. Выбери стратегию по риску: параллельная совместимость, adapter, read-old/write-new, expand/migrate/contract или ограниченный flag. Не требуй двухсторонний rollback, если он создаёт больший риск; опиши реально безопасный recovery path.
4. Задай milestones с критериями, а не произвольной датой: новый путь доступен; внутренние consumers переведены; внешние уведомлены, если это поручено; старое использование равно согласованному порогу; backup/restore и integrity checks выполнены.
5. Переводи потребителей небольшими самостоятельными шагами. Для данных считай записи до/после, проверяй выборки и повторяемость; для API — contract tests и error/access paths.
6. Удаляй старый путь только после доказанного нулевого/согласованного использования, пройденного окна наблюдения и явного разрешения на breaking/destructive шаг.
7. После удаления ищи остаточные ссылки, запускай затронутые проверки и контролируй runtime signals.

## Выход

Верни inventory consumers, compatibility matrix, этапы с entry/exit criteria, telemetry, data validation, recovery/rollback и доказательство завершения.

- **PASS** — потребители учтены, совместимость и данные проверены, exit criteria выполнены.
- **FAIL** — есть активный потребитель, потеря/расхождение данных, неподдерживаемый breaking change или нерабочее восстановление.
- **INCONCLUSIVE** — внешнее использование/состояние данных нельзя измерить; удаление блокируется, безопасная подготовка может продолжаться.

| Запрещено | Разрешено |
|---|---|
| Объявить старый API неиспользуемым по одному поиску | Совместить code search, runtime usage и реестр внешних consumers |
| Сразу удалить legacy после добавления нового | Дождаться измеримого exit criterion |
| Делать destructive migration без backup/recovery | Проверить восстановление пропорционально риску |
| Назначать дату без владельца и сигналов | Использовать milestones и наблюдаемое использование |

Правильно: новый reader понимает обе версии, writer пишет новую; после миграции счётчики и выборка совпадают, старое чтение исчезло. Неправильно: переименовать поле и исправлять клиентов после ошибок production.

Пример владельца: при повторной CMS-попытке нужно использовать существующие record IDs, а не создавать дубликаты; миграция сначала доказывает identity и совместимость.

Главное: удаление — последний доказанный шаг миграции, а не её начало.
